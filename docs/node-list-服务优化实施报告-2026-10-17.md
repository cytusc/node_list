## 2. 逐项实施方案

### 2.1 risk/attributes 消费者配置化

**问题**：`runner.go` 将 KindRisk/KindAttributes/KindLifecycle/KindRecovery 消费者硬编码为 1/通道。ip-service 的 risk 车道实测完成 ≈5/h vs 到期 ≈44/h，排队 1,053——全系统唯一结构性落后 lane。

**方案**：
- `Config.LaneConcurrency map[string]int`（config.go）：`<角色前缀>_<KIND>_CONCURRENCY` 优先于通用 `<KIND>_CONCURRENCY`，默认 1（与旧行为逐字节一致）。
- `Runner.laneCount(kind, high)`（runner.go）取代原特殊分支；探测 lane 仍用共享并发。
- Compose 为 ip-service 设 `IP_SERVICE_RISK_CONCURRENCY=2`（每优先级通道 2、共 4 消费者）；`IP_SERVICE_ATTRIBUTES_CONCURRENCY` 等 knob 一并文档化于 `.env.example`。

**并发安全核查**（实施前逐项确认，非假设）：
- `mergeAttributes` 有 per-IP `pg_advisory_xact_lock` + `SELECT ... FOR UPDATE`（observations.go:89-93）——risk 与 attributes 同 IP 并发合并不会丢字段。
- `ASNCache` 互斥 + 同 ASN 单次合并（exitip.go:783-807）。
- risk 的 `QueryIPPure` 不经 `ipcheck.Client` 的 `mu`——该锁持有整个 provider 调用（sources.go:108-109），意味着 **attributes 并发的收益仅限于数据库侧重叠**（provider 调用仍串行），这也是本次只调 risk 的原因。

**预期收益**：risk 完成率 5/h → 20/h+（4 消费者；若仍不达标则证明瓶颈在 Mihomo 实例租约而非消费者数，见 §4 验证）。

**风险**：低。默认 1 不变；生产仅 ip-service 的 risk 从 2→4 消费者；失败模式是 PG 连接池争用（已被 2.3 扩容对冲）。

### 2.2 API 看板 TTL 缓存

**问题**：`/api/services`（前端 15s 轮询）与采集状态（5s 轮询）每请求对 58K 行 work 表做多 FILTER 计数重聚合（source.go:127-148），多 Tab 下纯浪费。

**方案**：
- 泛型 `ttlCache[T]`（cmd/node-explorer/main.go）：TTL 内直接返回；**失败不缓存**（瞬时故障下个请求即恢复）；持锁加载使并发未命中合并为单次查询。
- 默认 `API_SERVICES_CACHE_SECONDS=10`、`API_COLLECTOR_CACHE_SECONDS=5`（均可用环境变量覆盖）；TTL < 前端轮询间隔的设计使单 Tab 也不会吃到过期数据意义上的不一致（多 Tab 才享受缓存合并）。
- `api.WriteServices` 改收 `Statuses` 接口（api/services.go），仓库实现直接满足，缓存包装在 main.go——响应形状、错误码、`Cache-Control: no-store` 均不变。

**预期收益**：多 Tab 场景下 statuses 聚合查询量降 80–95%；API 进程 CPU 与 PG xact_commit 同步下降。

**风险**：低。看板数字最多陈旧 10s/5s（服务心跳阈值 90s，无判断影响）。

### 2.3 连接池 6→8

**问题**：`PGPOOL_MAX` 默认 6，而 connectivity/ip-service 常驻 1 个控制器所有权连接（runner.go:64），实际可用 5；work 表 58K 行下 schedule+Publish+写入并发易打满。

**方案**：compose.yaml 默认 `${PGPOOL_MAX:-8}`；`.env.example`、MODULAR_SERVICES.md 同步。PG 侧 max_connections=100，六服务 × 8 = 48，余量充足（部署后 §4 复核）。

**预期收益**：任务高峰不再因池耗尽排队；为 risk 扩容提供头部空间。

**风险**：低。纯扩容；`runner.go:61` 的 `PGPOOL_MAX>=2` 断言不受影响。

### 2.4 schedule()：结构改动实施后否决 + 间隔杠杆

**原计划**（分析 §2.1/§4）：两阶段化——先按 `checked_at` 列做保守到期过滤，再仅对到期子集取 payload 解码，预期把每 5s 的 1,462 行 × 3 payload 压缩到 ~5 行。

**实施与回退过程**：
1. 实现落地（`dueCandidates` + `scheduleWork` 两阶段，共享 scope 谓词常量）。
2. **首次在真实 PG 上运行测试套件即失败 9 个用例**——包括 `TestIndependentCadenceAndManualRetirementScheduling`、`TestSchedulerBackfillsMissingTrafficRatioWithCooldown`（3 子例）、`TestUnsupportedShareLink...`（4 子例）等。
3. 失败分析确认根因是**设计假设错误**：schedule 是**预排模型**——每轮必须为所有可用节点 ① 预先创建 work 行（新节点/被清剿的行）、② 把 done 行刷新到未来 due（防立即重排）、③ 对 queued 行应用住宅优先级提升（分类翻转 → 5 分钟 cadence）。按"到期"跳过会同时破坏三者。我原判断"risk 刷新由 recur()/scheduleIP 自持"只覆盖了部分场景，测试固化的契约比分析更严。
4. **已回退为全量扫描**，仅保留零语义变更优化（移除无消费方的 `ORDER BY n.identity`），并新增 `SCHEDULE_INTERVAL_SECONDS`（默认 5s）作为调节杠杆——若 §4 观测显示 schedule 仍是热点，可改 10s 半量，无需发版。

**这个否决过程本身的附带发现（重要）**：本机缺少 `NODE_EXPLORER_TEST_PG` 时 `testutil.Postgres` 直接 `t.Skip`——**此前所有"service/api 测试通过"都是空跑**。本次在 WSL（ubuntu-gn，Go 1.26.1 + PostgreSQL 16，Go 与 PG 同时钟）重建了真实测试环境，`go test -race ./...` 14 包全绿。此前 Windows 上另有两个假失败源：WSL 与主机时钟残差（claim 类用例抖动）、gofmt 版本差异（CI 用 go.mod 的 1.26.1）。

**预期收益**：净零语义变更 + 一个零风险调节杠杆。

**风险**：无（回退后与 v1.4.11 行为一致，除 ORDER BY）。

### 2.5 发布链断点修复

**问题**：`91b89fb` 删除四个空 overlay 后，`.github/workflows/release.yml` 的打包步骤仍硬编码 `compose.pgsql.yaml compose.ippure.yaml compose.patrol.yaml compose.patrol.pgsql.yaml`——打 tag 后 CI 的 `tar` 会失败，发布链断裂。

## 4. 生产部署与效果验证（部署后执行）

**部署路径**：tag v1.4.12 → CI 发布 ghcr 镜像 + GitHub Release → 生产 `update.timer`（AUTO_UPDATE=true）拉取 latest → `deploy/update.sh` 滚动更新六服务，失败自动回滚。

**验证指标与基线**（基线取自 10-17 13:46–14:10 实测）：

| 指标 | 基线 | 验证方法 | 预期 |
|---|---|---|---|
| risk lane 完成率 | ≈5/h（queued 1,053） | `work` 表 done 行 5 分钟窗采样 ×2 | ≥20/h 且 queued 下降 |
| work 表 queued 总量 | 5.8 万（risk 1,053） | 部署后 1h/24h 对比 | risk 子集持续下降 |

**判定规则**：若 risk 完成率仍 <10/h，则瓶颈不在消费者数而在 Mihomo 实例租约（risk 与 exit 争用 normal lane 4 实例），后续方向是实例分区而非继续加消费者——此判定本身即为本次验证的产出之一。
