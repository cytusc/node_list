# node_list 三方库替代评估

日期：2026-10-23
范围：`backend/` 中自研的基础设施代码，对照成熟 Go 生态库

## 1. 结论摘要

| 结论 | 内容 |
| --- | --- |
| 值得换（P0，本周） | 供应商配额限流 → `golang.org/x/time/rate` + Redis 令牌桶；HTTP 重试 → `hashicorp/go-retryablehttp` |
| 值得换（P1，最大收益） | 任务账本 `node_explorer_work` → `riverqueue/river` |
| 值得换（P2） | 熔断/健康判定 → `sony/gobreaker`；观测 → `prometheus/client_golang` |
| **不该换** | 退避阶梯 `retryIntervalFor`、按 key 的确定性抖动 `spreadDue`、`ASNCache` |

一句话：真正"重造轮子"的是**任务队列**和**配额限流**；退避与抖动虽然也是自研，但它们承载的是领域策略（终态结果、确定性幂等），换成通用库反而更难读。

## 2. 为什么现在提这件事

今天三处线上问题，全部出在自研基础设施的边界条件上，而不是业务逻辑：

1. **空集合**：`carriers()` 返回空时 `for` 循环一次不执行，`queryErr` 保持 nil，走进成功分支解引用 nil `verdict`，进程 panic，`exit-attributes` 崩溃重启 31 次。
2. **阈值**：`spreadDue` 对一分钟级的容量等待也加抖动，打乱两条既有断言的精确窗口，CI 从 v1.5.50 红到 v1.5.52。
3. **抖动窗口**：退役波峰的 39k 行曾经全挤在同一小时，靠手工 SQL 摊平。

这类问题的共同点：**边界语义由我们自己定义、自己维护、自己回归**。库的价值不在于算法更难，而在于这些边界已经被成千上万的生产环境踩过。

## 3. 逐项评估

### 3.1 任务账本 → `riverqueue/river`（P1，收益最大）

现状：`node_explorer_work` 表 + `Claim/Finish/recur/once` + `generation` 乐观锁 + `lease_until`，共约 600 行，实现了：

- 唯一任务（`UNIQUE(kind,key)`）
- 租约与过期重领（`state='running' AND lease_until<now()`）
- 重试与退避（`attempts`、`retryIntervalFor`）
- 周期性重排（`recur` → `generation+1`）
- 优先级双车道

这正是 `river` 的核心模型（Postgres 后端、`UniqueOpts`、`JobRetryPolicy`、`PeriodicJob`、租约与优雅停机）。代价也确实存在：

- `work` 表 133k 行占 **1.05 GB 堆 + 228 MB 索引**（823 B/行），其中绝大部分是 `done` 历史；river 自带保留策略（`JobRetentionPolicy`）。
- 今天的"退役波峰"问题，river 用 `RunAt` + 调度器天然分散，不需要手工哈希摊平。
- 迁移成本：**高**。所有 kind（exit/risk/attributes/recovery/normal-recovery/cleanup/fast/live）都要改写，`recur` 的语义要映射到 river 的重试策略，双写过渡期至少一个版本。

建议：不立即动。先做 P0，再单独立项，用"新增 kind 走 river、存量 kind 保留"的渐进方式验证。

### 3.2 供应商配额 → `golang.org/x/time/rate` + Redis 令牌桶（P0）

现状：`node_explorer_provider_limits` 表记录冷却时间，调用前查表、命中 429 就写回一个粗粒度 `quota-cooldown`。实测 20 分钟内 ip-api 119 成功 / **744 次 quota-cooldown**，ipinfo 851 次冷却 / 0 成功——说明限流器本身在放大失败：一个进程被限后，其他进程仍继续撞墙。

方案：

- 单进程内用 `rate.Limiter`（已可用的 `golang.org/x/time/rate@v0.10.0`）做前置闸门，`Allow()` 不过就直接跳过，不再发请求；
- 跨进程用 Redis 令牌桶（`redis/go-redis` 已是依赖）保存每供应商的剩余额度，429 时 `SetNX` 一个与 `Retry-After` 对齐的冷却键；
- 表退化为审计用途，不再参与实时判定。

收益：直接消掉 744/863 的无谓请求，减少上游封禁概率。成本：约 150 行，`ipcheck` 一处调用点。

### 3.3 HTTP 重试 → `hashicorp/go-retryablehttp`（P0）

现状：`IPPureClient.get` 手写 429/5xx 重试（最多 2 次、指数退避、`Retry-After` 上限 5s），约 30 行。

换成 `retryablehttp` 后：`RetryMax`、`RetryWaitMin/Max`、`Backoff`、`CheckRetry` 全部现成，且默认带抖动、支持自定义 `HTTPClient`（继续复用每租约的代理 transport）。签名挑战（`x-k`）循环仍需自研，那部分是真业务逻辑，不该外包。

注意：`retryablehttp` 默认也重试网络错误，需要显式 `CheckRetry` 限制为 429/5xx，否则会把"节点不可用"伪装成"上游慢"。

另有一处集成风险必须先处理：现有 `fetch()` 用 `cancelOnCloseBody` 把请求上下文绑定到响应体关闭，注释明确写了"取消太早会作废签名挑战、丢掉可复用连接"；而 `retryablehttp` 自己会读干并关闭响应体。直接替换会让挑战循环拿到已关闭的 body。可行路径是让 `retryablehttp` 只负责 429/5xx 的重试决策，响应体仍由我们包装，这需要改造 `fetch()` 的返回契约——所以这项排在 P0-1 之后，单独一个 PR。

### 3.4 熔断与健康 → `sony/gobreaker`（P2）

现状：管理器里的 `healthy`、`rejected`、`quarantined`、`ErrManagerBusy` 各自表达一种"暂时别用"，没有统一的状态机，也没有半开探测。

`gobreaker` 的 Closed/Open/Half-Open 正好覆盖，且能和 3.2 的限流共用一套指标。

### 3.5 观测 → `prometheus/client_golang`（P2）

现状：所有指标靠手写 SQL 查 `work` / `ip_attributes` / `service_status`，排查时现写查询（今天写了十几个临时 SQL 文件）。

Prometheus 客户端 + 一个 `/metrics` 端点，能让"风险成功率、按模式的分布、租约占用、队列深度"变成常量查询，而不是每次临时拼 SQL。

## 4. 明确不换的三处

### 4.1 `retryIntervalFor`（退避阶梯）

```go
if result == "capacity-timeout" { return time.Minute }
if result == "config-rejected-dead" { return 1 << 62 } // 终态
if result == "config-rejected" { return max(base, 6*time.Hour) }
```

`cenkalti/backoff` 的 `ExponentialBackOff` 只能表达 base → ×N → ceiling 这一段；上面的终态、按结果类型分档都是领域策略。硬套会变成"库管一段、我们管另一段"，比现在更难读。**保持自研，但补测试**（已补：`TestNormalRecoverySpreadsRetirementWave`）。

### 4.2 `spreadDue`（按 key 的确定性抖动）

抖动必须是**按 key 确定**的：同一个任务第二次排期必须落在同一时刻，否则 `scheduleNormalRecovery` 每次 tick 都会挪动全部截止时间，幂等性直接崩。通用库的 jitter 是随机的，不满足这个约束。这里用 `fnv` + Postgres `hashtext()` 是正确的，问题只在阈值（已修：<1 小时不打散）。

### 4.3 `ASNCache`

80 行，同时做了 singleflight 合并、TTL、失败负缓存（30s 冷却）。`x/sync/singleflight` + `golang-lru/v2/expirable` 拼起来只能覆盖前两项，负缓存还得自己写，净收益为负。保持自研。

## 5. 执行顺序

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0-1 | `x/time/rate` + Redis 令牌桶替换 provider 冷却判定 | 20 分钟窗口内 `quota-cooldown` 降到 <50 次，成功数不下降 |
| P0-2 | `go-retryablehttp` 替换 IPPure 手写重试 | 现有 `collector` 测试全绿；429 场景行为不变 |
| P1 | river 渐进迁移（先新增 kind，再迁 risk/attributes） | 双写期数据一致，`work` 表停止增长 |
| P2 | gobreaker + prometheus | 熔断有半开探测；关键指标可在 `/metrics` 查到 |

## 6. 依赖可用性

已确认：`proxy.golang.org`、`goproxy.cn`、`goproxy.io` 均可达（HTTP 200），CI 侧无网络限制。

本地模块缓存已有：`golang.org/x/time@v0.10.0`、`golang.org/x/sync@v0.24.0`、`hashicorp/golang-lru`。

需要新增下载：`github.com/hashicorp/go-retryablehttp`、`github.com/riverqueue/river`、`github.com/sony/gobreaker`、`github.com/prometheus/client_golang`。

注意：本机 `GOPROXY=off` 是刻意的离线约定，引入新依赖时需要显式开代理拉取并提交 `go.sum`，CI 不受影响。
