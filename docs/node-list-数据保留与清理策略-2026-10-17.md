# node_list 数据保留与清理策略

> 2026-10-17 制定。原则：**先分类、再定保留期、后删除；每张表先问"删了会坏什么"，再问"能省多少"。**
> 本文档只定义策略与执行方案，**任何删除动作执行前需按第 6 节决策点确认**。

## 1. 结论（TL;DR）

- 生产库当前 **539MB**，其中 **65% 集中在两张表**：`ip_type_clean_backup`（249MB，46%）+ `ippure_results`（99MB，18%）。
- 已执行（2026-10-17）：`ip_type_clean_backup` 完成归档 + RENAME；DROP 定于 10-24（一次性自动化），届时 **539MB → ~290MB**。
- **`retired_nodes` / `node_registry` / recovery done 行不是垃圾，是系统记忆，禁止删除**（证据见第 3 节）。"91.7% 已退役"不等于"91.7% 可删"。
- 其余表的保留机制**已在生产正常运行且实测健康**（第 4 节）——策略的大框架已经在代码里跑着，缺的是**成文、补漏、监控**，不是从零建设。

## 3. 三个"不能删"的证据（针对"直接删除无效节点"的设想）

**① `retired_nodes` 是 API 与排程的排除名单——删行 = 节点复活。**
`internal/store/postgres/live.sql:23` 与 `internal/service/probes.go:59` 都是
`WHERE n.available AND NOT EXISTS(SELECT 1 FROM node_explorer_retired_nodes r WHERE r.identity=n.identity)`。
退役行一删，该身份立即重新进入活集视图和探测排程。share-link/subscription 源 churn 极高（这正是 v1.3.44 离开面板过滤要解决的问题），**源里再次出现 = 复活**，与"退役即永久排除、只有 recovery 链路可回"的设计相悖。

**② `retired_nodes` 同时是 recovery 复评的候选源，done 行是持久评估标记。**
`internal/service/schedule.go:91-99`：residential 角色的候选扫描条件为
`t.identity IS NOT NULL AND (t.reason=RetireRestoreReason OR t.reason LIKE 'IPPure:%')`，
且 `NOT EXISTS(recovery work 行)` 去重。`schedule.go:164` 注释原话："Keep completed tasks as
durable markers; each retirement is checked once." `source.go:166` 的 `pruneCompletedWork`
也**特意跳过** recovery 行（`kind<>'recovery'`）。这 14,256 行 done 是"这个退役身份已评估过"的记忆，删了会引发全量重评风暴。

**③ FK 锚定 + 时间戳会刷新，"旧退役行"这个筛选条件本身不成立。**
`connectivity`/`exits` 均有 FK → `node_registry`（restrict），删 registry 必须先删这两张排程数据源。
且实测 **16,071 行 retired_at 全部落在最近 5 天内**——重复退役会刷新时间戳，不存在"沉睡多年的退役行"可供按时间裁剪。6.9MB 的体量也没有清理收益。

**结论：retired_nodes 与 node_registry 永久保留。**"清理无效节点数据"的实际靶子只有第 5 节的 P0。

**已知语义副作用（记录在案，不视为 bug）**：lifecycle_events 30 天窗口意味着 `source.go:146`
的 restore 计数是"近 30 天滚动值"而非历史累计；看板上该数字会随时间回落到 0。

**ippure_results 定性更正**：此表并非遗留冻结表。`postgres.go:392` 每次快照导入写入、
`postgres.go:489-537` Reconcile 时按节点索引重挂（避免重导丢失 enrichment、重复烧 IP 查询配额）、
`projection.go:359` 投影消费。51,430 行 = 518 个活快照 × ~99 节点/快照，零孤儿（FK 强制），
99MB 是 7 天快照窗的固有成本。

## 5. 清理执行方案

### P0 — 归档 + RENAME（✅ 已于 2026-10-17 18:13 CST 执行）

1. `pg_dump -Fc` 归档至 `backups/postgres/ip-type-clean-backup-20261017.dump`（**8.4MB**，
   249MB 的 JSON 文本压缩比 ~30:1），`pg_restore -l` 校验 7 个 TOC 条目（TABLE + TABLE DATA + PK）齐全；
2. 依赖检查：0 个视图引用、无 FK（与全仓代码 grep 一致）；
3. `RENAME TO node_explorer_ip_type_clean_backup_archive` 已执行，184,163 行原样保留；
   RENAME 后 6 个服务全部健康（service_status 无 error）、explorer 日志无 error/panic；
4. **库容仍为 539MB——RENAME 不回收空间**，DROP 才是回收点（→ ~290MB）。已建 2026-10-24
   一次性自动化完成最后一步（校验归档存在 + 行数未变后 DROP）；
5. 归档文件不受 pg-backup.sh 的 14 份轮换影响（轮换只匹配 `node-explorer-*.dump`）。

### P1 — 小代码改动

4. `cmd/ip-type-clean` 工具去留——**原计划归档，调研后修订为保留**（2026-10-17）：
   它并非死代码：`README.md:84-94` 有完整用法、`deploy/ip-type-clean.sh` 是现成运维包装，
   功能是"刷新全部存量出口 IP（含退役）的七家实时查询"——P0 清理的只是它 10-15 那一次
   运行的陈旧回滚。且 RENAME 后它若再运行会 `CREATE TABLE IF NOT EXISTS` 建原名新表，
   回滚语义天然正确。**遗留改进建议（未实施，需用户确认）**：工具运行结束不清理自己的
   备份表（本次 249MB 即如此累积），建议下版增加"成功完成后自动 DROP 备份表"或
   `--keep-backup` 开关，从源头避免同类堆积；
5. `deploy/pg-stats.sh` 增加表体积日志（✅ 已实施并部署生产）：每次运行时除原行数日志外，
   追加 `backups/postgres-table-sizes.log`（TOP8 表总体积，含索引）。2026-10-17 已推送
   生产并实跑验证，首行即把 `_archive:249MB` 顶到榜首——观测本身生效。

### P2 — 待评估（只调研，不动手）

6. `ippure_results` 99MB：enrichment 缓存保留期 = 快照窗（7 天）——**调研结论：暂不收紧**
   （2026-10-17）。读者有三：`changes.go:58` ReadChanges（全量读加载全部快照的
   enrichments，增量读按 `results_changes` 的 snapshot_id 加载）、`postgres.go:489`
   Reconcile（按节点索引重挂被改批次的 enrichments）、快照 7 天 prune（projection.go:492，
   删除即触发重建）。收紧到"仅最新 1-2 个快照"的代价：departed 节点的属性寿命从 7 天
   缩到几分钟、增量读遇到已删快照会拿到缺 enrichments 的批次、Reconcile 重挂老批次时
   丢缓存重新烧 IP 查询配额。收益 ~95MB，但 P0 后库容 ~290MB 已健康——**用 95MB 换
   "不动工作正常的保留机制"不划算**。触发条件（满足其一再评估）：库容再次成为问题，
   或快照窗本身因其他原因要缩短。
7. `SNAPSHOT_RETENTION_DAYS`（7 天）是否最优：同时影响 snapshots 68MB + ippure 99MB +
   results_changes，与"历史快照回放"需求（若有）权衡。
