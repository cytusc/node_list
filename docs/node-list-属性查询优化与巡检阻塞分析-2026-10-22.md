# 属性查询优化与巡检阻塞分析（2026-10-22）

本文记录属性查询优化、巡检阻塞分析及随后获准实施的后台巡检改造。recovery 保留；代码未发布或部署。

## 服务职责与 recovery 的必要性

`compose.yaml` 中 `node-explorer` 使用镜像默认 PHP/webman 入口，处理查询请求。它关联数据库中的当前检测记录，不负责主动全量检测。

`mihomo-manager` 默认在上一轮完成后间隔 30 分钟启动全量巡检，更新 fast/connectivity 证据、累计失败轮次及提交退役，并为满足条件的已退役节点创建恢复标记。

`recovery` 消费恢复标记、普通恢复、fast/connectivity 依赖及 lifecycle 任务。恢复流程要求新鲜连通性证据、真实出口核验、按模式检查属性、再次核验出口稳定性，然后投递重新上架任务。清理协调器也使用这些依赖。因此不能在当前架构下直接删除该容器。若以后合并服务，应迁移这些消费者和状态转换；可以复用巡检结果减少重复探测，但仍须保留恢复正确性校验。

源码入口：`backend/internal/service/runner.go`、`recovery.go`、`sweep.go`，以及 `webman/start.php`。

## 属性查询已实施修改

- 六个来源并发查询，结果仍按原顺序返回；同一上游串行执行，保留限流和缓存去重。
- 缓存互斥锁只保护内存读写。网络请求、注册表演示 key 获取、限流等待均不持有该锁，缓存命中不必等待正在执行的网络请求。
- 等待上游执行位置支持 context 取消，避免已经超时的任务继续排队请求。
- `ipinfo.check.place` 的三种公共数据库查询共享执行位置、额度与拒绝冷却；个人 AbuseIPDB API 使用独立额度。不同数据库仍各自保留证据，不因共用传输上游而合并分类记录。
- HTTP 401/403 冷却 15 分钟；429 遵循上游重试时间；网络错误冷却 30 秒。拒绝冷却期间维护清洗模式也跳过请求，避免等候 15 分钟。
- 冷却使用现有 PostgreSQL provider limits 在进程间共享；请求被取消后仍用独立、最长 3 秒的清理上下文保存冷却。
- 批量 IP-API 缓存初始化不再重置其他上游的冷却记录。

这些修改降低无效请求与队头阻塞，不代表公共 API 的 403/429 已被解除。查询结果仍遵循现有分类规则，失败来源弃权，不伪造成功证据。

- `go test ./...`：通过（需要专用外部环境的集成用例仍遵循项目原有跳过条件）。
- `go build ./cmd/...`：通过。
- `BenchmarkLookupSources`：模拟每个上游请求 20ms、公共镜像拒绝；相同新客户端分别采用串行及并行编排，5 次迭代分别约 81.2ms、20.5ms，耗时减少约 75%。这是本地编排对照，不是线上吞吐提升承诺，也不是旧版本完整实现的基准。

## 全量巡检是否需要优化

结论：需要优化配置同步的响应时间；没有证据要求优先提高巡检并发或新增容器。

### 现有证据

沿用本轮前序线上诊断的数据，而非修改后的线上测量：

- 08:52:55—08:55:55，7 次采样没有等待超过 1 分钟的到期任务，未见过期运行租约或数据库锁阻塞。
- 当时巡检候选约 18,276 条；上一轮结果的探测时间分布在 08:24—08:31，不能把这段时间直接当作数据库事务耗时。
- 共享 Mihomo 在巡检阶段达到约一个 CPU 核心的使用量。仓库 Compose 默认限制该容器为 1 CPU；是否需要调整线上配额，应另行结合实际 CPU throttling 数据判断。

改造前，`mihomo_manager.go` 的主循环先读取注册表、调用 `Sync`，随后同步调用 `sweepAll` 和 `sweepCommit`。这两个函数返回之前，主循环不能再次检查配置变化。心跳在独立 goroutine 中继续更新，故健康状态正常并不能说明配置同步及时。

巡检并发默认 32，每项上下文最长 8 秒；整轮上下文最长 2 小时。18,276 项全部接近超时时，仅按 32 并发估算探测部分约需 76 分钟；这是容量边界估算，不是已观察到的耗时。`nextSweep` 在启动时推进，若单轮超过 30 分钟，下一轮可能紧接着开始，进一步压缩空闲时间。

### 改造前直接后台运行的风险

1. `Manager.Sync` 会暂停新租约、排空现有租约并更换 generation；`Delay` 在此期间可能返回 busy、取消、过期等错误。
2. 当前 `sweepAll` 把执行错误也转换为失败记录，`sweepCommit` 会写入连通性并累计失败轮次。
3. `sweepRetire` 有 generation 检查，但该检查没有覆盖此前的连通性与失败轮次写入。因此仅把巡检丢到 goroutine 中，会引入无效检测证据污染状态的风险。
4. 当前整轮集中事务提交；单纯异步探测也不能消除同步提交阶段的等待，事务耗时须单独测量。

### 已实施的方案

保持一个 manager 和一个共享内核，最多一轮后台巡检：

1. 主循环继续按 5 秒节拍检查注册表，巡检单独运行并报告进度。
2. 发现配置变化时，取消当前巡检并等待它退出；丢弃未完成轮次，然后执行 `Sync`，避免探测与重载竞争。
3. 巡检结果绑定 generation、incarnation。取消、busy、基础设施错误和过期代际不计入节点失败轮次；提交与重载之间保留互斥或明确的串行交接。
4. 下一轮按完成时间加间隔调度，避免慢轮次完成后立即再次占满执行资源。
5. 心跳加入轮次阶段、候选数、有效观察数、起止时间、总耗时、探测耗时和提交耗时。提交仍使用单事务；不扩大并发或调整容器 CPU。固定 worker 池替代每节点一个 goroutine。

验收应包括：巡检期间修改注册表可被主循环及时发现；取消/重载不会新增失败轮次或误退役；不存在重叠巡检；停机可退出；配置加载失败可回滚。上述后台运行及证据防护已实现；配置加载失败仍沿用 Manager 原有回滚路径。正常完成或失败从结束时起计间隔；配置重载取消的轮次可在新配置稳定后重新开始。已完成提交不因后续取消而撤回，重载始终等待整轮退出。

## 巡检与重载互斥修订（2026-10-22）

生产新增约两万节点后，观察到来源刷新触发重载，取消了已运行近 18 分钟、尚未提交的巡检。重载策略改为优先完成当前轮次：`sweepRunner` 使用进程互斥锁保护读取候选、探测和事务提交，配置循环通过非阻塞方式尝试取得同一把锁；忙时保留并合并最新配置，等本轮结束后再重载。上文“已实施的方案”中的“配置变化取消当前巡检”策略由此替代。服务心跳和配置变化检查继续运行。

`SWEEP_INTERVAL_SECONDS` 默认 1800 秒，从本轮结束时起算；例如 11:00 开始、11:20 完成，下一轮最早 11:50 开始，确保至少 30 分钟空闲窗口。配置重载不会提前开启下一轮。心跳新增 `sweep.next_run_at`，运行中待本轮结束后确定。停机、所有权连接丢失及两小时轮次超时仍会取消任务，现有代际、实例和配置摘要防护保持生效。

本次修订已通过 UTF-8 临时 PostgreSQL 上的 `go test -race ./internal/service ./internal/transport -count=1`、`go vet ./internal/service ./internal/transport` 和 `git diff --check`。回归包含探测/提交期间推迟重载、重载读取已提交结果、重载失败释放锁、完成后 30 分钟间隔及停机退出。
