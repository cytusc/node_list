# node_list 采集分析补充：IPPure 探测队列积压与 AE 待检测根因

- **分析时间**：2026-10-14 16:07 – 16:45 CST（paramiko 方式连接 89.106.76.82）
- **结论先行**：三个采集源（Qilan / subs-check / GitHub Patrol）执行全部正常；问题在 **IPPure 探测环节吞吐不足**——待检测 2114/4286（49.3%），其中 AE 16 个节点自入库起跨越 136 个快照从未被探测，属**排队饿死**，不是代码 bug。

## 三、AE 16 个待检测节点的特征（证据）

1. **从未被探测**：这些 identity 在快照 23–215（136 个快照，跨越多天）中反复出现，ippure_results 中 **0 条记录**；近 2h 全AE 仅被碰到 2-3 次（还是头部边缘节点）。
2. **全部 share-only**：有 rawLink、无 rawConfig（Qilan 分享链接节点）。
3. **快照内 index 位置固定偏后**：每轮 5 个在 index 106-230（头部边缘），6-7 个在 index 510-890（尾部）。例：快照 215 的 AE 待检测 index = 148,166,184,187,210,670,746,773,806,819,824。
4. 对照组：同批快照中 US 待检测 831 个，近 2h 被探 434 次——量大但头部节点确实在被消化。

## 四、根因链（容量饿死，非 bug）

1. **吞吐预算有限**：concurrency=10（代码允许的上限），单 job 出口探测+风险查询约 10-30s；`collect()` 在每个 wave 边界检查 `snapshotChanged()`——**Qilan 每 15 分钟到达的新快照会直接中断整轮采集**。结果写入时间线呈"突发 3-8 分钟 → 空档 3-7 分钟"模式，与快照时刻（:07/:22/:37/:52）严格对齐：每 15 分钟实际只消化 **~130-210 个探测**（≈500-800 次/h）。
2. **需求侧持续涌入**：每轮 Qilan 906 节点中 ~890 个待检测（其中约 680 个是上一轮起就排队的存活链接）；**分享链接约 15% 轮换**（214→215：139 条消失 / 111 条新生，10 轮累计 224/906 换新）→ 每轮有新 identity 注入队首。另有 ~135 次/h 的 error 重探（attempts≥2 的 6h/24h 退避到期）+ 148 个 success 缺 country 的回填。
3. **排队规则放大不公**：优先级 = (从未检测 ? 2 : 0) + (在最新聚合视图 ? 1 : 0)，同优先级按**快照内 index 顺序**（稳定排序）。每轮预算只够摸到 index ~130-180 的位置。
4. **AE 结构性饿死**：尾部组（index 510-890）永远超出每轮预算；头部组（106-230）在预算边缘时灵时不灵。而链接轮换/快照切换让它们的位置基本不变 → **从第一天起就没进入过探测名额**。
5. **排除的假说**：①"过期重探霸占队列"不成立——线上 `EXIT_IP_PROBE_VERSION=1` 与全部 808 条 error 的版本一致（非 outdated，优先级 4 队列为空）；②error 节点不霸队——663 个处于 6h 退避、134 个 24h 退避，大部分时间在睡觉；③缺配置不成立——最新快照 890 个待检测全部有 rawConfig/rawLink。

## 五、修复选项（按杠杆排序）

| # | 措施 | 效果 | 风险 |
|---|---|---|---|
| 1 | **部署已提交未发布的出口超时 8s→5s 补丁**（commit d73bfdb，v1.3.41 未含） | 死节点最坏探测 16s→10s，吞吐 +~30% | 极低（已有测试） |
| 2 | **放宽 snapshotChanged 中断**：当前 wave 跑完再退出（或允许跨快照跑完队列） | 消除每 15 分钟的重排+重 configure 空档（每段浪费 3-7 分钟） | 低（需小改 ippure.js） |
| 3 | **公平排序**：priority-3 内部按"首次出现时间"排序，或按 country 轮转 | 小国家节点不再被结构性饿死，AE 类问题根治 | 中（改排队策略需观察） |
| 4 | 链接轮换治理：若 Qilan 轮换链接是同一节点的临时凭证，identity 增加 (server,port,name) 二级归一 | 减少 ~15% 无效涌入 | 中（同 server 多节点有误合并风险，需评估） |
| 5 | UI 层：待检测展示"排队中"状态/位置 | 管理预期，减少误报"没处理" | 无 |

**建议**：1+2 尽快部署（纯吞吐提升，低风险）；3 排入下个版本（公平性根治）；4/5 观察后决定。

## 六、附：关键查询口径

- 待检测 = `current_nodes.payload->'ippure' IS NULL`（投影表 payload 直接挂最新结果）
- 每快照待检测 = `jsonb_array_elements WITH ORDINALITY`  LEFT JOIN `ippure_results ON (snapshot_id, node_index=ord-1)`
- 探测吞吐 = `ippure_results.payload->>'checkedAt'` 按小时/分钟分桶

## 七、措施 4 实施前评估（17:12-17:40，结论：否决不实施）

> 措施 4 原文："若 Qilan 轮换链接是同一节点的临时凭证，identity 增加 (server,port,name) 二级归一"。前提是「若」——实测否决。

### 数据证据（容器内 Node 脚本，canonical identity = 去 hash + 参数排序，12 快照 209-221 / 约 3 小时跨度）

| 指标 | 数值 | 含义 |
|---|---|---|
| distinct identity（跨度内） | 1050 | 去重后的真实连接数 |
| distinct (server,port,name,type) 键 | 929 | 归一化后的"节点"数 |
| 多变体键（1 键多 identity） | 83（8%） | 主要是**共存变体**而非先后轮换 |
| 新 identity 匹配"上一窗口刚消失键" | **几乎全为 0**（11 窗口中累计 2 次） | 无"上一轮换发" |
| 新 identity 匹配"跨度内任何已离开键"（复用） | **5 / 1050 = 0.5%** | 临时凭证轮换假设不成立 |
| 共存变体组内凭证比较 | 15 组 / 36 行：10 组同凭证、**5 组不同 uuid** | 同键不同凭证 = 真实不同账号，合并即误合并 |

### 修正此前结论

- 之前"15% 轮换（139 消失/111 新生）"是按 **raw link 原文**统计，把 #fragment 差异、参数顺序、面板成员进出全算成了轮换。canonical identity 层面的 churn 是**面板成员真实进出**（节点上/下线），新 identity 是真新节点，本来就该进队列探测。
- 即：**待检测积压的涌入侧没有"无效涌入"可治理**——措施 4 的收益前提不存在。
- 附带观察：快照节点总数 15 分钟内 845→701→766 大幅摆动，疑似 Qilan 抓取分页不稳定（不影响 identity 稳定性，同链接重现为同 identity，无队列副作用），可另行排查。

### 否决理由（成本收益）

- 收益上限：UI 去重 ~21/750 行（2.8%）+ 捕捉 0.5% 凭证复用；对队列涌入无改善。
- 成本与风险：6309 条 retired 身份迁移、patrol 状态重置（全量重查一轮）、identity 永久失去凭证区分度、且数据证实同键不同 uuid 的误合并场景真实存在（news.zoom.us:2096 两个 uuid）。
- 结论：维持现状（share-link 完整连接哈希 identity）。v1.3.42 的吞吐×3 + FIFO 已是正确杠杆；若未来观测到 Qilan 改为凭证轮换模式（同键重发率显著上升），再按本节口径复测后重启此项。
