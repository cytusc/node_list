# Xray 优先、Mihomo 兜底方案评估

> 实施更新：新服务见 [独立节点测活](../service-refactoring/10-node-liveness.md)。本评估中的恢复、生命周期和删除联动建议已被用户要求的完全解耦方案替代；观测数据仍为历史评估结果。

日期：2026-10-26  
范围：当前 PostgreSQL 节点数据、内核配置兼容性、HTTPS 连通性和双内核分流方案。  
状态：完成分析与独立实测；未修改业务代码、切换生产内核或写回节点状态。

## 结论

**当前节点集不适合由 Xray 全量替换 Mihomo，但适合评估“兼容配置优先 Xray，失败交给 Mihomo 复核”的双内核方案。**

错峰运行能降低瞬时负载。真正减少 Mihomo 请求的条件是：Xray 对兼容节点检测成功后，本轮连通性检测即可结束；明确不兼容的配置直接进入 Mihomo，避免无效的前置尝试。

当前实测证明了协议和配置覆盖存在缺口，也证明部分节点可通过 Xray 完成检测。**尚未证明双内核能提升生产吞吐或降低总 CPU 消耗。** 是否值得实施，需要使用常驻内核和真实调度方式进一步压测。

## 数据范围与实测方法

- 数据库快照时间：北京时间 2026-10-26 16:34:14。
- 范围：`node_explorer_node_registry` 中仍关联现存快照的 8,359 个节点；其中 `available=true` 为 952 个，存在退役记录的为 112 个。两种状态并非互斥。
- PostgreSQL 连接设置默认只读，并在 Repeatable Read、Read Only 事务中读取；未使用会运行迁移的业务 Adapter。
- 使用项目现有 `domain.ShareLinkProxy` 解析缺少 `rawConfig` 的分享链接，再通过独立实验转换器生成 Xray 配置。统计中的解析与转换限制不能全部归因于内核能力。
- 内核：Xray **26.10.21**；Mihomo **v1.19.27**，与生产版本一致。
- 全量执行 Xray 配置校验；按协议、数据库可用状态、传输方式、Reality、插件和混淆等特征分层，选取 274 个节点进行双内核网络测试。
- 使用独立临时内核进程、回环监听端口，网络测试并发为 8；每个内核进程设置 `GOMAXPROCS=1`。
- 两个目标均使用 HTTPS GET：`https://www.gstatic.com/generate_204` 要求 HTTP 204；`https://github.com/` 要求 HTTP 200 且 curl 成功完成。连接超时 8 秒、请求总超时 12 秒，目标站点 TLS 证书正常验证。
- 两个内核按节点交替测试顺序。首轮前后，以及差异复测期间，主机直连两个目标均成功。
- 对两个内核都能加载配置、但任一目标结果不同的 11 个节点，再进行两轮交替顺序复测，复测并发为 4。

该实验用于判断兼容性和当前连通表现，不执行节点失活确认、恢复或退役。GitHub 整页下载是补充测试，比收到响应头或 gstatic 204 成功更严格，不能混为同一判定口径。

Xray 26.10.21 已支持 **Hysteria2**，不能沿用旧版“不支持 Hysteria2”的判断。本次对应的 90 个配置通过校验，抽样中也有实际请求成功。

上述结论绑定测试版本。旧版 Xray 可能具有不同能力与限制，本轮未验证旧版，不能直接外推。

## 双内核连通性结果

首轮 274 个样本的统计如下。配置拒绝、解析失败和转换器未支持均单独记录，未标记为节点死亡。

| 指标 | Xray | Mihomo |
| --- | ---: | ---: |
| 配置加载成功并实际测试 | 165 | 257 |
| gstatic GET 成功，HTTP 204 | 111 | 172 |
| GitHub GET 成功，HTTP 200 且下载完成 | 98 | 162 |
| 两个目标均成功 | 96 | 158 |

两个内核都能加载的 **165 个样本**中：

| gstatic 结果组合 | 节点数 |
| --- | ---: |
| 两边成功 | 108 |
| 两边失败 | 53 |
| 仅 Xray 成功 | 3 |
| 仅 Mihomo 成功 | 1 |

其余结果差异主要来自协议、配置和实验转换器覆盖。AnyTLS 样本中，有 **6 个节点通过 Mihomo 成功访问两个目标**，构成不能全量替换的实际证据。

11 个差异节点的两轮复测完成后，gstatic 没有出现连续三次固定偏向某一内核的差异，说明不能根据单次失败认定某一内核不兼容或节点失活。

另有一个 VMess/WebSocket 节点在 Xray 下三次都通过 gstatic，GitHub 也均收到 HTTP 200，但整页下载达到 12 秒超时；Mihomo 三次完成下载。这是响应体传输表现差异，不能解释为 Xray 无法建立该节点连接。

## 推荐的分流和错峰方式

### 按完整连接配置判定能力

不能只按 `type=vless`、`type=ss` 等协议名称分配内核。应同时检查 TLS、Reality、传输方式、加密方法、ECH、插件、混淆和链式代理等参数。

能力结果应绑定 **内核版本与配置摘要**。节点配置或内核版本改变后重新判定，避免永久沿用过时的“不支持”记录。

| 情况 | 推荐处理 |
| --- | --- |
| Xray 支持协议及完整连接参数 | 优先交给 Xray |
| 明确不支持的协议或配置 | 直接交给 Mihomo |
| 当前解析链无法获得有效配置 | 单独记录解析问题；不能以此证明节点失联 |
| Xray 对指定目标检测成功 | 本轮连通性记成功，结束该项检测 |
| Xray 超时、握手失败、配置拒绝 | 交给 Mihomo 复核，暂不累计节点失败 |
| Xray 进程异常、服务不可用或队列满 | 记基础设施异常，转交或延后检测 |

### 独立队列持续运行，启动时间适当错开

建议 Xray 与 Mihomo 分别设置并发预算和队列，错开周期任务的启动时间。Xray 检测失败后及时进入 Mihomo 兜底队列。

不建议等待整轮 Xray 完成后再启动整轮 Mihomo，否则前一轮慢节点会推迟所有兜底请求。独立队列也应有统一的整机资源上限，避免两个内核同时扩并发造成 CPU、内存或连接数竞争。

Mihomo 应保留兜底配额，并优先处理近期可用、住宅和接近失败判定阈值的节点。重复投递需要合并，同一节点同一轮只产生一个最终连通性结论。

### 保留现有证据与生命周期防护

- Xray 与 Mihomo 在同一轮都失败，最多累计一次失败；继续沿用现有多轮确认、退役及删除前复核要求。
- Xray 配置拒绝和内核故障属于准备或基础设施问题，不能直接计为节点失联。
- 转交 Mihomo 后，只有符合现有检测契约的有效观测才能参与失败累计；不能把调度超时当作节点失败。
- 交接期间若节点配置、incarnation 或 generation 变化，应丢弃过期结果；沿用租约、配置摘要和写回校验。
- 指定目标连通成功不代表完成节点恢复。恢复仍须执行现有强出口验证，不能被双内核连通性成功替代。
- 两个内核须采用一致的目标、方法、预期状态码、目标 TLS 验证与响应体处理口径。记录实际使用内核及兜底原因，才能解释差异。

## 可能收益与成本

按首轮 gstatic 结果进行静态推演，假设配置加载失败及明确不支持的节点直接进入 Mihomo，Xray 实际测试失败后再转交 Mihomo：

| 样本范围 | 节点数 | Xray 实际测试次数 | Xray 成功、省去 Mihomo 的次数 | Mihomo 兜底次数 | 两内核合计测试次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全部分层样本 | 274 | 165 | 111 | 163 | 328 |
| 其中 available=true | 130 | 63 | 60 | 70 | 133 |

全部样本中，Mihomo 网络请求可能减少 **40.5%**，但合计网络测试次数相对单内核增加 **19.7%**。数据库标记可用的样本中，Mihomo 请求可能减少 **46.2%**。

这些数字是按既有样本结果推演，**不是实际运行双队列后的收益**。它们不包含配置准备、兜底排队和后续重试成本；样本为分层抽样，也不能直接外推全库成功率。

Xray 能减轻 Mihomo 请求压力，不代表降低总工作量。若节点大量失效，先在 Xray 等待超时，再在 Mihomo 等待复测，会增加资源开销和最终判定延迟。

HTTP/SOCKS 占数据库多数，也适合另行评估标准库原生检测的成本。不过当前生产配置将任务路由到 ManagedEngine，不能因为项目保留 NativeEngine 实现，就认为这些节点已在生产绕过 Mihomo。

## 实施前应验证的指标

后续如决定实施，应先用常驻内核和与生产一致的请求契约做独立压测，比较：

- 整轮扫描墙钟时间及节点完成时间 P95、P99。
- Xray 成功率、明确不兼容比例、实际 Mihomo 兜底比例。
- Mihomo 请求数、排队时间及住宅通道等待时间。
- 失败节点从首次尝试到最终有效观测的时间。
- 整机 CPU、可用内存、连接数及两内核分别的资源消耗。
- 复测后的结果差异，以及配置变化、租约过期、取消、内核故障时能否正确丢弃过期证据。

本轮逐节点临时启动内核，没有生产常驻批量调度的成本结构，不能用于宣布吞吐提升或选择最终并发数。
