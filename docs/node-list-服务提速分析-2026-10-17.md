# node_list 各服务提速分析（2026-10-17）

- **分析方式**：本地代码走查（全部结论带 `文件:行号`）+ 生产 5 轮只读核查（paramiko，无任何变更）。
- **生产版本**：v1.4.11 六服务架构（API + source/connectivity/ip/residential/lifecycle 五角色 worker + Redis + 16 Mihomo + 外部 PG）。
- **一句话结论**：**系统当前没有"积压病"，只有"结构税"**——IPPure 积压已清（待检测 2,114 → 14），活节点集按名义周期健康运转；可提速的是三笔固定开销（每 5s 全量调度扫描、每秒投递重排、每任务一次代理重载）、一个落后 lane（risk 消费者被钉死在 1）和一处 API 每请求重复聚合。

> **实施勘误（2026-10-17 晚，v1.4.12）**：本文 §2.1/§4 建议的"schedule() 改 SQL 到期集 / 两阶段过滤"**已被实施并否决**。真实 PG 测试套件（`TestIndependentCadenceAndManualRetirementScheduling` 等 9 个用例）证明 schedule 是**预排模型**：每轮必须为所有可用节点预先创建 work 行、把 done 行刷新到未来 due、并对 queued 行应用住宅优先级提升——按到期跳过会同时破坏三者。结构改动已回退，改为保留全量扫描 + 新增 `SCHEDULE_INTERVAL_SECONDS` 调节杠杆；第一梯队的其余项（risk 消费者配置化、看板 TTL 缓存、连接池 6→8）已实施。详见《服务优化实施报告-2026-10-17》。

## 0. 测量口径说明（先读这段，否则数字会误读）

生产多张表是 **upsert 表**（一身份一行，反复更新）。`count(*) WHERE checked_at > now()-interval '24 hours'` 数的是**被碰过的不同身份数**，不是更新事件数——直接用它算吞吐会低估约 20 倍（本文初版即因此得出错误的 142/h）。

本文采用的定标方法：

| 方法 | 用途 |
|---|---|
| 5 分钟窗去重计数（两次采样） | 瞬时更新速率 |
| `work` 表 `due_at` 分布 | 名义周期达成率、是否积压 |
| `pg_stat_user_tables` 扫描计数 | PG 侧真实扫描压力 |
| `/api/services` | 各服务任务在途/逾期快照 |

**已核实的自洽画面**：活节点集 ≈1,462（`available` 且在 7 天快照留存内、未退役），全部在未来 30 分钟内到期、**0 逾期**；瞬时更新速率 connectivity ≈3,072/h、exit ≈4,100/h、attributes ≈432 IP/h。即：**名义周期（普通 1800s / 住宅 300s）正在被达成，队列是平衡的**。

## 2. 系统级共同税（三个服务共享，优先治理）

### 2.1 schedule() 每 5 秒全量联结 + 全量 JSON 解码

`service/schedule.go:87-96`：每个探测角色（connectivity / ip / residential）每 5 秒执行一条**四表全量 JOIN**（registry ⋈ connectivity ⋈ exits ⋈ ip_attributes ⋈ retired），`WHERE n.available AND EXISTS(快照)` 过滤后**把每个活节点的 3 份 JSON payload 拉回 Go 进程逐个 Unmarshal**（`schedule.go:107-147`），再在本地决定间隔/优先级并装配 work（`schedule.go:148-174`）。

- 规模：3 服务 × 12 次/min × ~1,462 节点 × 3 份 JSON ≈ **25 万份 JSON 文档/分钟**的传输+解析，加上 PG 侧对 registry 17K 行的反复联结过滤（活节点只占 9%）。
- 这是全系统最重的周期性固定开销，且与"有多少任务真正到期"完全解耦。

**提速方向**：把「读全量 → 本地决策」改为「SQL 内按 `next_due <= now` 直接算到期集」。注意 residential 判定（`domain.FreshResidential`，schedule.go:148）依赖 attr/exit payload，需在 SQL 内复现或预置物化列——这是主要改造量。建议先记录 pg_stat 基线再动。

### 2.2 Publish 每秒窗口函数重排

`service/repository.go:92-101`：每服务每秒对 `node_explorer_work` 执行 `row_number() OVER (PARTITION BY kind,(priority>0) ORDER BY …)` 全窗口排序 + `unnest` 四数组 UPDATE fencing。work 表 3.25 亿次索引扫描的主要制造者。六服务常驻 = 6 次/秒。

**提速方向**：① 主 ticker 内 Publish 节流到 2s（投递延迟 +1s，扫描减半）；② 窗口函数改为「只对 due_at<=now()+10s 的行排序」的部分索引/CTE 收窄；③ work done 行保留 2 天 → 1 天（source.go:56-61，churn 高时表体积直接减半）。

### 2.3 连接池与语句超时

`store/postgres/postgres.go:114-125`：每进程池上限 6，但每个探测服务用 1 条长连接常驻做 controller 咨询锁（`runner.go:58-94`），**实际可用 5 条**；`statement_timeout=30s`。ip-service 瞬时并发（8 exit + 2 分类消费者 + 每秒 Publish + 每 5s schedule + 心跳 + BeforeProvider 事务）峰值可触及 5 条上限，pgxpool 排队表现为尾延迟；若 work 表继续涨到 Publish 超过 30s，会被直接掐断并出现「Redis 任务投递暂时失败」。

**提速方向**：`PGPOOL_MAX` 6→8（env 一行，无需改码）；长期仍靠 2.1/2.2 降压。

## 3. 逐服务分析

### 3.1 API 查询（node-explorer）—— 健康，一个小杠杆

**现状**：live 路径单 SQL 完成筛选/统计/分页（`store/postgres/live.go:129-154`，MATERIALIZED CTE + 全排序 `row_number` + facets），无 N+1、无内存折叠；`main.go:67` 装配 Live reader，`store.Aggregate` 折叠路径在生产不可达。**顺带正式结论：昨天遗留的「main.go 切 read-through store 接线」经核实无收益——API 主路径已是 SQL 投影，缓存 store 只承担 SourceWarning，该项关闭。**

**唯一定点问题**：`/api/results` 每请求执行**两条** SQL——live 查询 + `collector()` 触发的 statuses 聚合（`main.go:58-66` → `source.go:127-148`：对 58K 行 work 做多 `FILTER` 计数 + lifecycle_events 子查询）。前端每 5s 轮询、N 个 Tab 叠加时这是纯浪费。另 current_nodes 索引扫描 ≈216/s，显著高于预期查询量，需 `EXPLAIN (ANALYZE, BUFFERS)` 查明是单查询重复扫描还是外部流量。

**提速**：
1. statuses 结果加 2–5s TTL 缓存（多 Tab 共享）——每请求省一条重聚合，低风险；
2. live 查询做一次 EXPLAIN，核对 `nodes AS MATERIALIZED` 是否被多次扫（facets/tally/page_candidates 三个 CTE 各自引用）；
3. 如 2 命中，把 metadata/facets 与 page 合并为一次扫描或短时物化。

**预期**：轮询场景 PG 查询量 −40~60%；API 进程 CPU 本就不是瓶颈（<1%），收益在 PG 侧。

### 3.2 来源导入（source-ingest）—— 健康，一个系统性贡献

**现状**：10s 主 tick（`source.go:39`），`SyncRegistry` 有 revision 短路（`registry.go:28-33`）；ingest ≥30s；每小时清扫（probe_results 2 天 / done work 2 天 / lifecycle 30 天 / 快照 7 天，`source.go:54-63`）；Qilan 900s（容器实测）。

**它对全系统的最大贡献不是自己的速度，而是帮别人减税**：registry 17,042 行中 ~15.6K 是已退役/已离开的冻结身份，却仍在被 schedule JOIN 扫描（§2.1）。**在清扫任务中增加「registry 死身份归档」**（不在 current_nodes、无 retired 记录、无近期 work 的身份移入归档表或打标），可直接把 §2.1 的扫描面砍掉 ~90%。注意：retired 身份要保留（recovery 调度依赖），只清「从未退役但已离开」的。

**提速**：① 上述死身份清理（结构性，收益最大）；② 快照 7 天保留不变（ ingest 性能与历史完整性平衡点，勿动）；③ subs-check 实际周期 ~2h10m vs 配置 120s——这是 watcher 静默期语义不是故障，观察即可。

### 3.3 测活（connectivity）—— 名义周期已达成，余量在死节点

**现状**：8 消费者（4 住宅 + 4 普通，容器实测）；瞬时 3,072 更新/h ≈ 名义需求；0 逾期。单次探测 = Mihomo 重载 + `reachable()`（12s 超时）+ 失败后 10s 再探 + 必要时对照节点（`probes.go:96-126`）。**死节点最坏 12+10+12=34s**，活节点 ~2-5s。

**提速**：
1. **死节点快速失败**：对连续失败 ≥N 次的身份，把「重试 + 对照」降级为单次 6s 探测（对照逻辑保留给住宅/恢复 lane）。预计把最坏任务时长从 34s 压到 ~7s，直接释放消费者容量。**风险中**：`ConfirmedDead` 是退役触发条件（probes.go:146-152），需保证降级路径不产生误判的 confirmed-dead——建议只对「已有 confirmed-dead 记录或连续 error ≥3」的身份启用。
2. §2.1/2.2 共同税治理（它的 schedule 和 Publish 与 ip 服务同构）。

**预期**：消费者有效容量 +30~50%（取决于死节点占比），普通节点周期达成率更稳。

### 3.4 IP 属性（ip-service）—— 三 lane 三种命运，risk 是短板

**现状（实测）**：
- **exit lane**：4,100 更新/h，流畅。但每个任务是**单节点 reserve**（`probes.go:204`）→ `sameProxySet` 永不复用（`transport.go:411-414`，单节点指纹必不相等）→ **每任务一次 `PUT /configs?force=true` 全量重载**（`transport.go:420-448`，15s 超时 + YAML 渲染）。集群级 ≈1.14 次重载/秒。探测本身 75s 上下文 / 5s 每端点 / 8 端点竞速 4 批 / 2 次传输失败早停（`probes.go:225-227`、`collector/exitip.go:33-45,229`）——超时体系已经优化过，重载是剩余固定税。
- **attributes lane**：432 IP 更新/h，走 24h 缓存（`probes.go:289`），正常。
- **risk lane**：**消费者被硬编码为 1**（`runner.go:102-104`），每任务 2 次必打 IPPure（ip-basic + ip-risk）+1 可选、10s client、重试 1s→2s（`exitip.go:442-458`、`probes.go:339`）。完成 ≈5/h vs 到期 ≈44/h，1,053 排队——**ip-service 内部唯一结构性滞后**。
- 分类六源：单互斥串行 + per-provider 1500ms 节流 + `BeforeProvider` 每源一次事务（`ipcheck/sources.go:194`、`service/limits.go:25`）——attributes 消费者同样只有 1，但受 24h 缓存兜底不明显。

**提速（按杠杆排序）**：
1. **risk/attributes 消费者 1→2~4**（`runner.go:102-104` 改为可配置或直接调大）：risk lane 吞吐上限直接翻倍再翻倍。全局 1500ms/provider 限流是跨进程 DB 协调的，天然兜底不会打爆上游。**低风险，第一优先。**
2. **exit 任务批量重载（Mihomo wave 化）**：同通道到期任务打包 K=4~8 个，共享一次 `ConfigureProxyBatch`，逐节点用 `mixed-port+i+1` 独立 listener（`transport.go:449-461` 的端口机制已就绪）。重载从 1.14 次/s 降到 ~0.15-0.3 次/s；对 2-5s 的快任务占比高的场景，任务平均耗时省 ~10-20%。**中风险**：需改 Claim 为批量取 + 失败隔离（单节点配置被拒不能连坐同批，`transport.go:429-435` 的 ProxyConfigError 处理可复用）+ 租约覆盖整批。
3. 分类来源并行化：把单互斥链改为按源分 goroutine（每源自带 1500ms 节流），attributes 上限从 ~6 源串行 × (15s 超时 + 1.5s pacing) 中解放。中风险，随 1 一起做。
4. IPPure ip-basic + ip-risk 两必打调用如当前串行，可并行（需核 `exitip.go:585-613` 后小改）。

**预期**：risk 队列消化从 >24h 到 <6h；exit lane 有效吞吐 +10-20%；整体 ip-service 对「出口变化 → 分类就绪」的端到端延迟显著缩短。

### 3.5 住宅恢复（residential-recovery）—— 门控是设计，不要动

**现状**：每 lane 在途完整验证 <2（`repository.go:193-195` 准入锁）；实测 checked 1,589 / skipped 401（机房 ASN 批量跳过已是快路径）；单次验证 10-14 条单行 SQL、3min 超时（`recovery.go:15-125`）；等待前置结果 1s 轮询。

**提速**：
1. **修正准入计数语义**：当前计数包含「retry 后仍带 startedAt 的排队任务」（`repository.go:249-251` 不清 startedAt），准入门可能被排队任务占满导致有效并行 <2。只数 running 可恢复满额并行。低风险。
2. 验证内 Probe×2 串行（`recovery.go:62-67`）→ 并行。小收益。
3. 10-14 条单行 SQL 合并为 2-3 条批量查询——收益有限（验证耗时 dominated by 网络探测），列为可选。

**明确不要做**：不要提高准入门控上限——「一次完整验证合格即恢复」的完整性依赖在途数受控。

### 3.6 生命周期（lifecycle）—— 不是瓶颈

**现状**：退役 5 条 SQL/节点、恢复 8 条/节点，单节点事务无批量（`recovery.go:154-242`）；restored 346；retired 15,581 行（+~1,900/天）。按 1,900 退役/天 ≈ 1.3 次/min 的写入量，对 PG 无压力。`lifecycle_events` 索引扫描为 0（表小，全表扫描可接受）。

**提速**：无需专项。恢复速率受 §3.5 准入门控——联动受益。如未来退役量上量，再考虑批量退役事务。

## 5. 明确不做（防止过度优化）

1. **不调大 PROBE_TIMEOUT、不去重试**——误杀风险大于吞吐收益；死节点问题用 §3.3-1 的降级路径解决。
2. **不动 recovery 准出门控 <2**——完整性设计。
3. **不动 1500ms provider 限流与 24h IP 缓存**——上游配额与成本保护。
4. **不做 read-through store 进 API main.go 的接线**——已核实无收益（§3.1），遗留项关闭。
