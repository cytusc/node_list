# 独立批量连通性压测

本工具验证把每次一个节点改为不可变批次后，Mihomo 的重载次数、吞吐和判定一致性。线上服务、公共 API、数据库结构不变。它不执行恢复、退役或删除，也不代表节点已经通过强出口验证。

ShellCrash 是内核管理器，Zashboard 的快速检测主要调用 Mihomo delay API。该 API 使用 HEAD，不能直接代替本项目的 GitHub GET 证据。这里复用现有 `transport.MihomoEngine.Reserve`：每个节点独立监听端口，整个批次完成后才归还内核，禁止中途重载或切换全局 selector。

## 隔离边界

- 数据库仅在采样阶段连接，startup 参数和显式事务均强制 read-only；不调用 Adapter、Runner、Repository、Redis、迁移或任务领取。
- 采样结束即关闭数据库。执行检测的容器没有数据库网络和凭据。
- `cb-*` 专用控制器通过独立 Compose project 启动，不发布宿主端口。命令拒绝生产控制器名称以及两通道复用同一内核。
- 普通批次最多 128 个目标节点，另附对照；批次内原生 HTTP/SOCKS 和 Mihomo 共用通道并发预算。住宅通道使用另两个内核和独立预算；出口池不参与。
- 每次实际尝试最多 12 秒；首次失败后等待 10 秒；两次失败后必须通过主机直连和独立节点对照才能确认不可用。请求方法、URL、状态码及 TLS 策略复用现有实现。
- 对照节点在不同服务端之间分散选择，每批通常附带 8 个对照。只合并仍在执行的同一主机/同一 reference identity 的对照 GET，不缓存已完成结果；跟随者必须等待在其请求验证后完成的响应。实际对照 HTTP 并发单独限制为 16，住宅/普通通道各自隔离。请求的领导者同步持有批次租约，跟随者取消不会让请求越过租约。
- 首个 reference 失败时，在同一批次内顺序回退到其他独立服务端，最多尝试 3 个；每次仍有 12 秒超时，保留失败和成功轨迹及对应参考节点身份。主机直连必须成功，参考节点全部失败仍是证据不足。任何 HTTP 429 都会使分档运行失格，即使另一参考节点随后成功。
- 不记录原始代理错误、节点名称、IP、分享链接或凭据；结果仅用 identity 的 SHA-256 前 24 位关联。原始 sample 文件包含连接材料，只保存在服务器的 0700 私有目录，禁止提交 Git。

## 构建和运行

在 backend 目录构建静态程序：

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags '-s -w' -o connectivity-bench ./cmd/connectivity-bench
```

将程序和本目录 Python 文件复制到服务器的独立私有目录。`harness.py` 中的运行时镜像默认使用当前调优镜像，可按环境调整。该镜像只提供 CA/runtime，不运行生产入口。

```sh
python3 harness.py setup
python3 harness.py sample --output sample.json
python3 monitor.py > monitor.log 2>&1 &
python3 harness.py run --batch 1 --concurrency 16 --output baseline16.json
python3 suite.py > suite.log 2>&1
```

若修改原型后保留原始对比结果，可使用 `BENCH_PREFIX=bounded- python3 suite.py` 生成另一组结果文件。选择档位时还会排除对照不足或出现 HTTP 429 的运行，复测失格则回退并继续验证相邻低档。

采样按协议比例进行确定性分层，固定选取 128 个最近可用节点及 384 个已退役节点，不足则使用实际数量。另取 16 个最近可用的住宅节点同时施加负载。基线使用 20 个独立普通内核、并发 16；原型仅使用其中 4 个普通内核，依次测试并发 16、64、128、256、512。闲置内核会保留到结束，资源结果因此较实际 4 内核部署保守。

`suite.py` 对最快的合格档和相邻低档各追加两次复测，按三次平均吞吐比较，提升不足 10% 时选择低档。它逐节点比较各档结果，对差异节点交替运行两轮单节点模式和批量模式。若有差异，必须检查 `verify-*.json` 的每次尝试轨迹，再决定是否可以进行全量只读扫描；脚本不会仅凭总数一致宣告准确。

审核通过后，以新的只读事务捕获当时到期候选，再执行选定档：

```sh
python3 harness.py sample --due --output due-sample.json
python3 harness.py run --sample due-sample.json --concurrency 512 --output due-sweep.json
```

最后停止监测并清理专用容器。保留脱敏报告和必要的私有审计材料，删除私有 sample、控制器密钥和临时二进制：

```sh
touch stop-monitor
python3 harness.py down
```

这台 4 CPU / 20 GiB 服务器的最终实测选择为 4 个普通内核、128 目标批次、总并发 512，另外保留 2 个住宅内核；其他环境应重新执行分档和质量复核。[完整实测报告](../../docs/node-list-批量连通性压测-2026-10-19.md) 包含前两版未通过原因、最终复测及 6,619 个到期候选的实际扫描结果。

## 指标和门槛

`elapsed_seconds` 是整组目标从排队、配置到最终判定的实际墙钟耗时，吞吐为 count / elapsed。`queue_ms` 从该轮投递起算至获得检测配额，包含准备路径和排队；`assessment_ms` 是节点实际完整判定耗时加该批次准备耗时，不含等待检测配额。两者有准备时间重叠，不可直接相加。基线最早版本仅记录实际判定耗时，报告需明确该限制。`reloads` 是成功加载配置次数，不包括隔离坏节点时被内核拒绝的配置尝试；`control_requests` / `control_joins` 分别记录实际对照请求及合并的等待者数量。

| 指标 | 合格 | 自动停止当前档 |
| --- | --- | --- |
| 判定准确性 | 差异复核后没有新确认的错误判定 | 控制器错误比例 > 1% |
| 住宅排队 P95 | ≤ 5 秒 | — |
| 完整判定 P99 | ≤ 120 秒 | — |
| 整机 CPU 平均 | < 70% | > 85% 持续 30 秒 |
| 可用内存 | ≥ 4 GiB | < 2 GiB |

Go 监测器读取挂载的宿主 `/proc/stat`、`/proc/meminfo`，缺失监测数据即拒绝启动。JSON 中 TCP 数量属于探测容器网络命名空间，宿主连接数及各专用内核 CPU/内存另由 `monitor.py` 捕获。该脚本还只读监测生产普通/住宅队列。CPU 平均值包含同期生产负载，不能解释为压测本身 CPU 消耗。

## 后续生产集成约束

压测通过后仍需单独实施：统一巡检/住宅/非住宅的批次收集、优先级隔离、任务租约续期和批次取消；结果提交继续使用原有 incarnation、generation、lease 和配置版本防护。恢复仍要求两次独立强出口验证，真实删除前仍要求新鲜独立检测。还要调整恢复协调器的 admission：若协调器仍只允许 16 个在途 session，底层 128/256 并发无法得到足够任务。

本原型不持有生产租约，因此不会跳过这些防护写入结果；未来生产集成应沿用并回归现有相关测试。连通性全扫时间必须与强出口验证和实际恢复时间分别报告。
